# Agentic Harness проекта harness-demo

## Назначение

`harness-demo` демонстрирует управляемую агентскую разработку:

```text
цель → проверяемый план → loop → готовый результат
```

AI-агент пишет код и может уточнять план, но не определяет готовность сам.
Внешний Harness запускает проверки, защищает требования и тестовые данные,
фиксирует каждую итерацию в Git и решает, можно ли перейти дальше.

## Два режима

### Brownfield

На входе есть работающий код с недостающими функциями и подготовленный человеком
`PLAN.md`. Harness последовательно отдаёт агенту задачи и проверяет результат.

### Greenfield

На входе есть контракт `SPEC.md`, данные и acceptance-тесты, но каталог
`src/minisearch/` пуст. Агент сначала создаёт `PLAN.md`. Harness принимает план,
только если он:

- содержит проверку `done when` для каждой задачи;
- покрывает все acceptance-тесты;
- соблюдает порядок функций из спецификации;
- содержит проверки, которые действительно красные до реализации.

После автоматической валидации предусмотрено подтверждение человеком.

## Что разрабатывает Harness в этом проекте

Целевой продукт — локальная библиотека `minisearch`. В greenfield-режиме агент
должен последовательно создать:

1. **Core** — модель документа, загрузку JSONL, токенизацию, hashing embedder,
   cosine ranking, CLI и английский `recall@3` не ниже `0.8`.
2. **Persistence** — сохранение/загрузку индекса, CLI-индексацию и поиск по
   индексу из другого процесса.
3. **Russian** — обработку кириллицы и `ё/е`, нормализацию словоформ, русский
   `recall@3` не ниже `0.9` без регрессии английского.
4. **Language filter** — параметр `lang` в Python API и CLI.
5. **Result export** — выгрузку выдачи в UTF-8 JSON или CSV через CLI с
   сохранением в файл либо выводом в stdout.

Источником требований служат спецификация, acceptance-тесты и данные оценки, а
не готовая реализация.

## Что нужно предоставить для нового проекта

Минимальный входной комплект:

1. Git-репозиторий и воспроизводимый baseline-коммит.
2. `SPEC.md` с целью, контрактами и ограничениями.
3. Команды установки и общей проверки проекта.
4. Независимые acceptance-тесты.
5. Тестовые данные и ожидаемые результаты.
6. Измеримые критерии `done when`.
7. Список защищённых файлов и каталогов.
8. Разрешённые команды и действия агента.
9. Лимиты времени, итераций и повторных ошибок.

Для brownfield дополнительно нужен исходный `PLAN.md`. В greenfield его формирует
агент, но человек должен заранее подготовить спецификацию и проверочные оракулы.

## Какие исходные данные уже подготовлены

### Спецификация продукта

`SPEC.md` описывает конечную цель, публичные контракты модулей, порядок поставки
функций, ограничения, общую проверку, пороги качества и защищённые пути. Это
неизменяемый контракт между заказчиком и Harness.

### Корпус и наборы оценки

`data/corpus.jsonl` содержит русский и английский корпус:

```json
{"id":"...","text":"...","lang":"ru"}
```

`eval/en.jsonl` и `eval/ru.jsonl` связывают запросы с ожидаемыми релевантными
документами. Модуль `minisearch.evaluate` вычисляет `recall@3`. Пороги:

- английский — не ниже `0.8`;
- русский — не ниже `0.9`.

Агент не может менять корпус и эталоны ради искусственного улучшения результата.

### Автоматические тесты

```text
tests/
├── acceptance/
│   ├── test_core.py
│   ├── test_persistence.py
│   ├── test_russian.py
│   ├── test_lang_filter.py
│   └── test_export.py
└── harness/
    ├── test_plan.py
    └── test_validate_plan.py
```

Acceptance-тесты проверяют продукт, harness-тесты — парсер, изменения плана и
безопасность критериев.

## Файлы этого проекта

- `SPEC.md` — контракт поисковика и порядок поставки функций;
- `PLAN.md` — исполняемый план;
- `PROGRESS.md` — короткий журнал решений между свежими сессиями;
- `AGENTS.md` — паспорт проекта и команды проверки;
- `tests/acceptance/` — пользовательские критерии приёмки;
- `data/`, `eval/` — корпус и эталонные запросы;
- `.cursor/rules/` — правила работы и перепланирования;
- `.cursor/hooks/` — блокировка опасных действий и post-edit проверки;
- `harness/loop.py` — orchestrator;
- `harness/validate_plan.py` — валидатор greenfield-плана.

### `PLAN.md` — исполняемый план

Каждый пункт имеет идентификатор, состояние и объективный критерий:

```markdown
- [ ] T2 Index persistence
  - done when: `pytest -q tests/acceptance/test_persistence.py`
```

Первый незавершённый пункт становится текущей задачей. Галочку `[x]` ставит
только Harness после успешной внешней проверки.

### `PROGRESS.md` — память между сессиями

Агент добавляет краткое описание результата или решения:

```text
iter 2 T2: Index.save/load and CLI roundtrip implemented
```

Новая сессия не нуждается в истории предыдущего чата: состояние хранится в Git,
`PLAN.md`, `PROGRESS.md` и результатах проверок.

### `AGENTS.md` — паспорт проекта

Содержит версию Python, установку, общую команду проверки и ссылки на правила.
Это краткая точка входа для каждой свежей сессии.

### Cursor rules, commands и hooks

```text
.cursor/
├── commands/
│   ├── plan.md
│   ├── next-task.md
│   └── replan.md
├── rules/
│   ├── workflow.mdc
│   └── replanning.mdc
└── hooks/
    ├── guard.py
    └── after_edit.py
```

Workflow ограничивает сессию одной задачей, требует минимального изменения,
task-check, регрессии и записи в `PROGRESS.md`. Replanning разрешает добавить
дочернюю задачу при обнаружении зависимости или слишком большого объёма.

`guard.py` блокирует push, ручные коммиты, destructive reset, рекурсивное
удаление, `sudo`, загрузку с немедленным запуском и незаявленные зависимости.
`after_edit.py` запускает Ruff после изменения Python-файла.

## Plan phase в greenfield-режиме

Harness даёт агенту команду `/plan` и до трёх попыток по умолчанию. Валидатор
проверяет:

1. план не пуст;
2. идентификаторы уникальны;
3. у каждой задачи есть `done when`;
4. все задачи изначально не отмечены;
5. покрыты все acceptance-тесты;
6. команды входят в allowlist;
7. каждый критерий красный до начала реализации.

Последнее условие исключает пустые задачи и проверки, проходящие заранее. После
валидации Harness показывает план человеку. Только подтверждённый план
коммитится и передаётся в loop.

## Как работает loop

На каждой итерации Harness:

1. читает первый незавершённый пункт `PLAN.md`;
2. запускает новую изолированную сессию Cursor Agent;
3. передаёт одну задачу и её `done when`;
4. ограничивает время выполнения;
5. откатывает изменения защищённых путей;
6. самостоятельно запускает task-check и общую регрессию;
7. отмечает задачу выполненной только при зелёных проверках;
8. сохраняет метрики и отдельный Git-коммит;
9. переходит к следующей задаче.

Если задача раскрыла зависимость или оказалась слишком большой, агент может
добавить дочернюю задачу. Исходные пункты нельзя удалять или переписывать.
Следующая сессия читает обновлённые `PLAN.md` и `PROGRESS.md`, поэтому workflow
динамический, но его состояние остаётся обозримым.

## Правила динамического перепланирования

После сессии Harness сравнивает `PLAN.md` с версией в `HEAD`. Разрешено добавить
только незавершённую подзадачу вида `T2.1` с существующим родителем и собственным
безопасным `done when`.

Нельзя удалять задачу, менять её название или критерий, самостоятельно ставить
галочку либо добавлять новую задачу верхнего уровня. Недопустимые изменения
откатываются. Агент может адаптировать маршрут, но не переписать цель.

## Защитный контур

Агент не может изменять спецификацию, acceptance-тесты, эталонные данные и сам
Harness. Команды `done when` разбираются по allowlist и запускаются без shell.
Опасные команды блокируются hooks. Заявление агента «готово» не учитывается без
успешного внешнего теста.

Для настоящего greenfield-прогона используется `--strip`: reference solution,
демо-агент и готовые режимы физически удаляются из рабочей ветки, поэтому агент
не может скопировать решение.

Команды `done when` исполняются без shell. Для этого проекта разрешены только
`pytest`, `python -m minisearch.evaluate` и безопасные цепочки через `&&`.
После каждой сессии Harness дополнительно выполняет `make check`: Ruff, весь
pytest и английский evaluation.

## Требования перед запуском

- чистое Git-дерево и baseline-коммит;
- Python 3.10+ и dev-зависимости;
- Git;
- Cursor Agent CLI;
- авторизация Cursor и интернет на время разработки.

Сам поисковик после сборки работает без интернета. Сеть нужна Cursor Agent.

## Запуск на Windows

Требуются Python 3.10+, Git, Cursor Agent CLI, интернет и авторизация Cursor:

```powershell
py -3 --version
git --version
agent --version
agent status --format json

py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"

.\use_mode.ps1 greenfield
git add -A
git commit -m "greenfield baseline"
$env:AUTO_APPROVE = "1"
.\loop.ps1
```

Для ручного gate не задавайте `AUTO_APPROVE`: Harness покажет план и запросит
подтверждение до начала разработки.

### Brownfield-запуск

```powershell
.\use_mode.ps1 brownfield
git add -A
git commit -m "brownfield baseline"
.\loop.ps1
```

Здесь `PLAN.md` уже подготовлен человеком, поэтому plan phase пропускается.

### Изолированный реальный greenfield

Для контрольного запуска готовые материалы физически удаляются:

```powershell
.\use_mode.ps1 greenfield --strip
git add -A
git commit -m "stripped greenfield baseline"
.\loop.ps1
```

### Настройка лимитов

```powershell
$env:MAX_ITER = "12"
$env:MAX_FAILS = "3"
$env:ITER_TIMEOUT = "600"
$env:PLAN_TRIES = "3"
.\loop.ps1
```

`AGENT_CMD` позволяет подменить реальный CLI тестовым агентом.

### Linux и macOS

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
./use_mode.sh greenfield
git add -A && git commit -m "greenfield baseline"
./loop.sh
```

## Предсказуемая offline-репетиция

`demo/fake_agent.py` проверяет Harness без Cursor API:

```powershell
$env:AGENT_CMD = "py -3 demo/fake_agent.py"
$env:AUTO_APPROVE = "1"
.\loop.ps1
```

Сценарий показывает отклонение неполного плана, повторную генерацию,
динамическую подзадачу, попытку изменить защищённый путь и автоматический откат.
Это детерминированная демонстрация механики, а не доказательство качества AI.

## Артефакты и аудит

Результат сохраняется в ветке `loop/MMDD-HHMMSS`. Каталог `.loop/` содержит
логи сессий, результаты последних проверок и `metrics.csv` с длительностью,
кодами проверок, изменениями плана и нарушениями. Каждая итерация представлена
отдельным коммитом `DONE`, `FAIL` или `BLOCKED`.

```text
.loop/
├── metrics.csv
├── last_check.txt
├── last_regress.txt
├── last_failure.txt
└── runs/
    ├── plan-1.log
    ├── iter-1.log
    └── iter-N.log
```

`metrics.csv` содержит номер итерации, задачу, коды task-check и регрессии,
изменение плана, число нарушений и продолжительность. По логам можно восстановить,
что делал агент и почему Harness принял либо отклонил результат.

## Реальный контрольный прогон

Результат опубликован в ветке
[`loop/1008-130105`](https://github.com/Gryzly73/harness-demo/tree/loop/1008-130105),
а физически очищенный вход — в
[`greenfield-real-baseline`](https://github.com/Gryzly73/harness-demo/tree/greenfield-real-baseline).

Итог:

- агент самостоятельно создал и прошёл валидацию плана из четырёх задач;
- Core, persistence, Russian и language filter выполнены;
- 4 задачи закрыты за 5 итераций;
- одна сессия получила внешний `permission_denied`, следующая продолжила работу;
- нарушений защищённых путей — `0`;
- агентское время — 1034 секунды;
- 15 тестов, Ruff, EN recall `1.000`, RU recall `1.000`.

Реальный прогон подтвердил восстановление после внешнего сбоя. Динамическое
добавление подзадач воспроизводимо показывает offline-сценарий
`demo/fake_agent.py`; в реальном прогоне агенту перепланирование не понадобилось.

Этот контрольный прогон зафиксировал исходный план T1–T4. Позднее Harness был
расширен пятым acceptance-критерием `test_export.py`: новые greenfield-планы
обязаны включать отдельную задачу выгрузки JSON/CSV, а brownfield-план содержит
её явно. Историческая ветка прогона остаётся неизменяемым доказательством
первоначального цикла.

## Как адаптировать Harness

Для другого продукта необходимо:

1. заменить `SPEC.md` на контракт продукта;
2. предоставить исходный код или пустую greenfield-структуру;
3. подготовить независимые acceptance-тесты;
4. предоставить репрезентативные данные и эталоны;
5. настроить общую регрессионную команду;
6. расширить allowlist допустимых `done when`;
7. определить защищённые пути;
8. настроить установку и сборку;
9. выбрать лимиты и escalation policy;
10. провести offline-репетицию и настоящий контрольный прогон.

## Ограничения

Harness не компенсирует неполную постановку. Если требование отсутствует в
`SPEC.md`, тестах и метриках, система может принять формально корректный, но
неполный результат. Качество поставки напрямую зависит от качества входного
контракта и проверочного оракула.

Harness обеспечивает воспроизводимость, безопасность и аудит, но не заменяет
архитектурное решение заказчика и ручную приёмку критичных функций. Внешний
отказ Cursor, сети или лимитов фиксируется как `FAIL` и может потребовать
повторной итерации.
