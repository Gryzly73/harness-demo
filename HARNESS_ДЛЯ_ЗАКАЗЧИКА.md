# Agentic Harness проекта harness-demo

## Назначение

`harness-demo` демонстрирует управляемую агентскую разработку:

```text
цель → проверяемый план → loop → готовый результат
```

AI-агент пишет код и может уточнять план, но не определяет готовность сам.
Внешний Harness запускает проверки, защищает требования и тестовые данные,
фиксирует каждую итерацию в Git и решает, можно ли перейти дальше.

## Два режима

### Brownfield

На входе есть работающий код с недостающими функциями и подготовленный человеком
`PLAN.md`. Harness последовательно отдаёт агенту задачи и проверяет результат.

### Greenfield

На входе есть контракт `SPEC.md`, данные и acceptance-тесты, но каталог
`src/minisearch/` пуст. Агент сначала создаёт `PLAN.md`. Harness принимает план,
только если он:

- содержит проверку `done when` для каждой задачи;
- покрывает все acceptance-тесты;
- соблюдает порядок функций из спецификации;
- содержит проверки, которые действительно красные до реализации.

После автоматической валидации предусмотрено подтверждение человеком.

## Что нужно предоставить для нового проекта

Минимальный входной комплект:

1. Git-репозиторий и воспроизводимый baseline-коммит.
2. `SPEC.md` с целью, контрактами и ограничениями.
3. Команды установки и общей проверки проекта.
4. Независимые acceptance-тесты.
5. Тестовые данные и ожидаемые результаты.
6. Измеримые критерии `done when`.
7. Список защищённых файлов и каталогов.
8. Разрешённые команды и действия агента.
9. Лимиты времени, итераций и повторных ошибок.

Для brownfield дополнительно нужен исходный `PLAN.md`. В greenfield его формирует
агент, но человек должен заранее подготовить спецификацию и проверочные оракулы.

## Файлы этого проекта

- `SPEC.md` — контракт поисковика и порядок поставки функций;
- `PLAN.md` — исполняемый план;
- `PROGRESS.md` — короткий журнал решений между свежими сессиями;
- `AGENTS.md` — паспорт проекта и команды проверки;
- `tests/acceptance/` — пользовательские критерии приёмки;
- `data/`, `eval/` — корпус и эталонные запросы;
- `.cursor/rules/` — правила работы и перепланирования;
- `.cursor/hooks/` — блокировка опасных действий и post-edit проверки;
- `harness/loop.py` — orchestrator;
- `harness/validate_plan.py` — валидатор greenfield-плана.

## Как работает loop

На каждой итерации Harness:

1. читает первый незавершённый пункт `PLAN.md`;
2. запускает новую изолированную сессию Cursor Agent;
3. передаёт одну задачу и её `done when`;
4. ограничивает время выполнения;
5. откатывает изменения защищённых путей;
6. самостоятельно запускает task-check и общую регрессию;
7. отмечает задачу выполненной только при зелёных проверках;
8. сохраняет метрики и отдельный Git-коммит;
9. переходит к следующей задаче.

Если задача раскрыла зависимость или оказалась слишком большой, агент может
добавить дочернюю задачу. Исходные пункты нельзя удалять или переписывать.
Следующая сессия читает обновлённые `PLAN.md` и `PROGRESS.md`, поэтому workflow
динамический, но его состояние остаётся обозримым.

## Защитный контур

Агент не может изменять спецификацию, acceptance-тесты, эталонные данные и сам
Harness. Команды `done when` разбираются по allowlist и запускаются без shell.
Опасные команды блокируются hooks. Заявление агента «готово» не учитывается без
успешного внешнего теста.

Для настоящего greenfield-прогона используется `--strip`: reference solution,
демо-агент и готовые режимы физически удаляются из рабочей ветки, поэтому агент
не может скопировать решение.

## Запуск на Windows

Требуются Python 3.10+, Git, Cursor Agent CLI, интернет и авторизация Cursor:

```powershell
py -3 --version
git --version
agent --version
agent status --format json

py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"

.\use_mode.ps1 greenfield
git add -A
git commit -m "greenfield baseline"
$env:AUTO_APPROVE = "1"
.\loop.ps1
```

Для ручного gate не задавайте `AUTO_APPROVE`: Harness покажет план и запросит
подтверждение до начала разработки.

## Артефакты и аудит

Результат сохраняется в ветке `loop/MMDD-HHMMSS`. Каталог `.loop/` содержит
логи сессий, результаты последних проверок и `metrics.csv` с длительностью,
кодами проверок, изменениями плана и нарушениями. Каждая итерация представлена
отдельным коммитом `DONE`, `FAIL` или `BLOCKED`.

## Реальный контрольный прогон

Результат опубликован в ветке
[`loop/1008-130105`](https://github.com/Gryzly73/harness-demo/tree/loop/1008-130105),
а физически очищенный вход — в
[`greenfield-real-baseline`](https://github.com/Gryzly73/harness-demo/tree/greenfield-real-baseline).

Итог:

- агент самостоятельно создал и прошёл валидацию плана из четырёх задач;
- Core, persistence, Russian и language filter выполнены;
- 4 задачи закрыты за 5 итераций;
- одна сессия получила внешний `permission_denied`, следующая продолжила работу;
- нарушений защищённых путей — `0`;
- агентское время — 1034 секунды;
- 15 тестов, Ruff, EN recall `1.000`, RU recall `1.000`.

Реальный прогон подтвердил восстановление после внешнего сбоя. Динамическое
добавление подзадач воспроизводимо показывает offline-сценарий
`demo/fake_agent.py`; в реальном прогоне агенту перепланирование не понадобилось.

## Ограничения

Harness не компенсирует неполную постановку. Если требование отсутствует в
`SPEC.md`, тестах и метриках, система может принять формально корректный, но
неполный результат. Качество поставки напрямую зависит от качества входного
контракта и проверочного оракула.
